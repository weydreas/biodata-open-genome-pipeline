# Регламент агентной разработки через Git + CI

## Назначение

Этот документ фиксирует рабочую модель разработки, которая используется в Dante WGS pipeline и должна переноситься в другие проекты пользователя, если проект предполагает изменения кода через чат с обязательной регрессионной проверкой.

Цель модели — не просто хранить код в Git, а построить **замкнутый проверяемый контур**:

```text
задача
  ↓
отдельная ветка
  ↓
изменение кода
  ↓
PR/MR
  ↓
CI
  ↓
чтение конкретного run/job/log
  ↓
исправление при падении
  ↓
повторный CI
  ↓
GREEN regression gate
  ↓
merge в release-ветку
```

Главное правило: **красный CI никогда не является релизом и никогда не должен сливаться в release-ветку**.

---

## 1. Что здесь означает «агентный режим»

Чат не является постоянно работающим фоновым процессом. Он не продолжает самостоятельно работать после завершения ответа.

Под агентным режимом в этом регламенте понимается другое: в рамках активного рабочего хода ассистент способен выполнить полный наблюдаемый цикл разработки через доступный Git-коннектор:

1. прочитать актуальное состояние репозитория;
2. создать ветку от текущей release-ветки;
3. изменить код и тесты;
4. открыть PR/MR;
5. получить идентификатор CI run;
6. проверить отдельные jobs;
7. открыть лог упавшего job;
8. определить причину падения;
9. внести исправление в ту же ветку;
10. дождаться нового run;
11. убедиться, что все обязательные lanes завершились `success`;
12. проверить агрегирующий regression gate;
13. только после этого выполнить merge;
14. синхронизировать постоянную development-ветку с новым `main`, если использовался squash merge.

Нельзя подменять этот цикл фразами «тесты должны пройти», «CI запущен» или «похоже, всё хорошо». Для merge требуется **наблюдаемый конечный GREEN-результат для конкретного SHA**.

---

## 2. Ветки и релизная дисциплина

Рекомендуемая схема:

```text
main                 = только доказанно рабочие версии
feature/* или fix/*  = одна конкретная задача
PR -> main           = единственный обычный путь изменения main
```

Допустима постоянная ветка `develop`, но после squash merge она должна быть явно синхронизирована с новым `main`. Иначе история расходится, следующий PR начинает содержать старые уже слитые изменения и CI/compare становятся неоднозначными.

Правило для новой работы:

- feature/fix ветка создаётся **от текущего `main`**;
- в PR фиксируется head SHA;
- CI проверяется именно для этого head SHA;
- если после проверки head SHA изменился, предыдущий GREEN больше не является достаточным — проверяется новый run.

## 3. Архитектура CI

Чтобы чат действительно мог управлять разработкой через Git, checkout репозитория должен быть **достаточной тестовой единицей**.

Это означает: максимально возможная часть регрессионного набора должна выполняться на CI runner без доступа к пользовательскому компьютеру.

### 3.1. Обязательные свойства

CI должен:

- уметь установить runtime/dependencies из декларативных файлов;
- иметь deterministic unit/regression tests;
- не зависеть от случайного локального state;
- использовать synthetic fixtures для больших/приватных данных;
- отдельно тестировать OS-specific код на соответствующем runner;
- иметь один стабильный агрегирующий check, например `full-regression`;
- падать при падении любого обязательного lane.

### 3.2. Типовая схема

Для проекта с Python + Windows PowerShell:

```text
python-regression        ubuntu-latest
    compile/check
    unit + regression
    self-tests
    synthetic fixtures

windows-powershell       windows-latest
    parse/syntax
    Windows-specific contracts
    launcher/runtime checks

full-regression
    needs: [python-regression, windows-powershell]
    success только если success у всех обязательных lanes
```

Название агрегирующего check желательно сохранять стабильным между версиями workflow. Это упрощает дисциплину merge и позволяет позже включить branch protection без смены контракта.

---

## 4. Локальные и большие данные

Git CI не должен требовать загрузки приватных или тяжёлых пользовательских данных только ради тестов.

В репозиторий не должны автоматически попадать:

- patient data;
- VCF/BAM/FASTQ;
- медицинские архивы;
- локальные базы с чувствительными данными;
- большие reference datasets, если их распространение или объём делают это неразумным;
- API secrets.

Вместо этого CI получает минимальные синтетические fixtures, которые воспроизводят **семантический контракт** production-файлов.

Пример принципа:

```text
production: многогигабайтный reference file
CI: 5–50 строк с той же схемой и специально подобранными edge cases
```

Synthetic fixture не должен притворяться production-данными. Его назначение должно быть явно отмечено в коде/тесте.

---

## 5. Packaging-aware tests

Если production runtime строится из wrapper/base/template или генерируется при запуске, статический CI не должен тестировать не тот слой.

Нужен CI-only materialization step, который воспроизводит реальный deployment/runtime transform.

Принцип:

```text
source base
 + wrapper patches
 + release rules
 = runtime view
```

Legacy tests, которые читают итоговый runtime-файл, должны получать материализованное представление, максимально близкое к production.

При этом сам wrapper/base также следует отдельно проверять на syntax/parse, чтобы materializer не маскировал ошибку исходного deployment-кода.

## 6. Порядок работы ассистента над каждой задачей

### Шаг 1. Зафиксировать baseline

Перед изменением:

- определить текущий `main` SHA;
- проверить отсутствие неоднозначной divergence у рабочей ветки;
- понять, какие tests/gates являются обязательными;
- определить, изменяется ли analytical/scientific contract или только UI/orchestration/docs.

### Шаг 2. Создать отдельную ветку

Не писать рабочее изменение прямо в `main`.

Именование:

```text
fix/<short-description>
feat/<short-description>
docs/<short-description>
```

### Шаг 3. Изменить код вместе с regression contract

При bugfix необходимо проверить не только место конкретного падения, но и:

- аналогичные сценарии;
- последующие стадии;
- UI/status logic;
- deployment/package manifest;
- compatibility со старыми READY outputs, если analytical contract не менялся.

На исправленную ошибку должен появиться regression test, если это практически возможно.

### Шаг 4. Открыть PR/MR

В описании должны быть:

- причина изменения;
- что изменено;
- что намеренно не изменено;
- нужен ли пересчёт upstream outputs;
- какие tests являются acceptance criteria.

### Шаг 5. Наблюдать CI

Не достаточно увидеть `queued` или `in_progress`.

Нужно получить финальное состояние каждого обязательного job.

Если job упал:

1. открыть его log;
2. найти конкретный failing test/error;
3. отделить production regression от ошибки самого CI/test fixture;
4. исправить истинную причину;
5. commit в ту же branch;
6. проверить новый run с новым SHA.

### Шаг 6. Merge gate

Merge разрешён только если одновременно выполнено:

```text
PR mergeable = true
python-regression = success          # если такой lane есть
OS-specific lane = success           # если такой lane есть
full-regression = success
head SHA соответствует проверенному run
```

Нельзя ссылаться на GREEN старого SHA после нового commit.

### Шаг 7. После merge

- получить merge/main SHA;
- при squash merge синхронизировать `develop` с новым `main`, если `develop` используется;
- убедиться, что deployment source смотрит только на release-ветку;
- не заставлять пользователя вручную переносить файлы, если предусмотрен bootstrap updater.

---

## 7. Отделение кода от пользовательских данных

Для локальных приложений рекомендуется GitHub-first/GitLab-first bootstrap:

```text
local launcher
  ↓
fetch/reset скрытого локального repo cache до origin/main
  ↓
копирование только allowlisted deployment paths
  ↓
запуск локальной программы
```

Allowlist должен быть явным release manifest.

Updater не должен изменять каталоги типа:

```text
patients/
input/
results/
reference_data/   # кроме явно управляемых маленьких metadata/code artifacts
*.bam
*.vcf*
*.fastq*
*.sqlite*
.env
```

Таким образом Git отвечает за код, а локальное окружение — за данные и тяжёлые вычислительные artifacts.

---

## 8. Когда CI пока недостаточен

Наличие GitHub/GitLab само по себе ещё не означает, что проект готов к агентной разработке.

Если correctness можно проверить только локально из-за:

- недоступных CI больших файлов;
- LFS/state, не воспроизводимого runner'ом;
- специфического ПО на пользовательском компьютере;
- отсутствующего CI workflow;
- тестов, которые существуют только как локальный `.cmd/.ps1` и не перенесены в runner;
- невозможности ассистента наблюдать job/log/terminal state,

то временный безопасный режим действительно такой:

```text
локальный snapshot/archive
  ↓
изменение
  ↓
локальные тесты над snapshot
  ↓
только доказанно GREEN snapshot
  ↓
commit
```

Но это **fallback, а не конечная архитектура**.

Следующая инженерная задача должна состоять в переносе необходимых тестовых контрактов в наблюдаемый CI, чтобы вернуться к стандартной схеме этого документа.

---

## 9. Как поднять такой же контур в другом существующем проекте

Соседний чат, получивший этот документ, должен **не начинать с изменения бизнес-кода**. Сначала необходимо построить CI control loop.

### Фаза A — аудит

Нужно определить:

1. где находится canonical repo;
2. какая release-ветка;
3. какие локальные команды сегодня считаются полным regression test;
4. какие языки/runtimes используются;
5. какие тесты требуют Windows/Linux/Docker;
6. какие inputs слишком большие или приватные для CI;
7. какие из них можно заменить synthetic fixtures;
8. какие локальные build/package transforms нужно материализовать на runner;
9. какие artifacts должны оставаться только локальными;
10. как сейчас происходит deploy/update пользовательской копии.

### Фаза B — минимальный CI

Нужно создать workflow, который сначала просто повторяет существующие локальные тесты.

Не переписывать одновременно production logic и тестовую систему без необходимости.

Для каждого недоступного локального dependency:

- либо установить его на runner;
- либо создать synthetic fixture;
- либо вынести отдельный OS-specific lane;
- либо явно признать этот test local-only и оставить release gate неполным до следующего шага.

### Фаза C — агрегирующий gate

Добавить стабильный job:

```text
full-regression
```

который зависит от всех обязательных lanes и сам завершается failure, если хотя бы один из них не `success`.

### Фаза D — доказать контур

До использования CI для реальной разработки нужно сознательно проверить оба состояния:

1. заведомо корректный commit → GREEN;
2. временно внесённая тестовая поломка или dedicated negative fixture → ожидаемый RED.

После проверки RED поломка удаляется, новый run обязан вернуться в GREEN.

Это доказывает, что gate действительно ловит регрессию, а не просто всегда зелёный.

### Фаза E — перейти на PR workflow

После доказательства CI:

```text
main = release only
feature/fix branch = work
PR/MR = review + CI
full-regression GREEN = условие merge
```

Только после этого проект считается готовым к работе по Dante-модели.

## 10. GitHub Actions и GitLab CI

Принцип одинаковый; меняется только platform adapter.

### GitHub

Требуются операции:

- branch;
- commits/files;
- PR;
- Actions workflow runs;
- jobs;
- job logs;
- merge.

### GitLab

Эквивалент:

- branch;
- commits/files;
- Merge Request;
- pipeline;
- jobs;
- job trace/log;
- merge.

Если чат способен только отправить commit, но не способен получить конкретный pipeline/job/log и проверить финальный результат, это **не замкнутый агентный CI loop**. В таком случае использовать fallback с локально проверенным snapshot до появления наблюдаемого CI-интерфейса.

## 11. Обязательный текст задания для соседнего чата

Когда этот гайд применяется к другому проекту, инструкция ассистенту должна звучать так:

> Прочитай `AGENTIC_CI_WORKFLOW_RU.md` и сначала подними в этом проекте такой же замкнутый CI control loop, как в Dante WGS. Не меняй бизнес-логику до завершения инфраструктурной фазы. Найди существующие локальные regression tests, перенеси их contract в CI, замени недоступные большие/приватные inputs синтетическими fixtures, добавь необходимые OS-specific lanes и один стабильный агрегатор `full-regression`. Проверь, что ты можешь из чата создать ветку/PR, увидеть конкретный CI run и head SHA, открыть job logs, исправить красный run, получить новый GREEN и только после этого merge. Никаких merge при RED или `in_progress`. Если часть тестов пока невозможно воспроизвести в CI, явно перечисли этот gap и не объявляй pipeline полноценным до его закрытия.

После построения контура ассистент должен предоставить краткий acceptance report:

```text
Canonical repo: ...
Release branch: ...
Development workflow: ...
CI platform: ...
Mandatory lanes: ...
Aggregator: full-regression
Synthetic fixtures: ...
Local-only gaps: NONE / ...
Observed RED test: PASS
Observed GREEN recovery: PASS
PR -> CI -> log -> fix -> CI -> merge loop: PASS
Deployment/data isolation: PASS
```

Только `Local-only gaps: NONE` либо явно согласованный ограниченный residual gap позволяет считать миграцию законченной.

## 12. Самопроверка ассистента перед каждым merge

Перед нажатием merge ассистент обязан ответить себе на все вопросы «да»:

- Я знаю точный head SHA этого PR/MR?
- CI run относится именно к этому SHA?
- Все обязательные jobs завершены, а не просто стартовали?
- Я видел `success` агрегатора `full-regression`?
- После последнего GREEN не было нового commit?
- Я не загрузил в repo приватные пользовательские данные?
- Изменение deployment manifest соответствует новым/удалённым файлам?
- Если менялась только orchestration/UI, я не заставляю пересчитывать научные/тяжёлые outputs без причины?
- Если менялся analytical contract, версия/schema и stale logic обновлены осознанно?
- При squash merge development branch после merge будет синхронизирована с `main`?

Если хотя бы один ответ «нет» — merge не выполняется.

---

## 13. Основной принцип

**Git — не место, куда складывают непроверенный результат. CI — не декоративный информер.**

Рабочая единица разработки — это изменение, для которого существует воспроизводимая цепочка доказательств:

```text
конкретный SHA
→ конкретный regression run
→ конкретные successful jobs
→ GREEN full-regression
→ merge
```

Если такую цепочку невозможно построить, сначала чинится инфраструктура доказательства, а уже затем продолжается разработка продукта.
