# Dante WGS local pipeline v8.6.0


> История релизов и performance-настройки собраны в одном файле: `CHANGELOG.md`.
> **v8.6.0** keeps the resumable Stage 16 architecture from v8.1.0 and upgrades its analytical contract: every target locus is called against explicit REF/ALT hypotheses (`bcftools call -C alleles`), homozygous-reference confidence uses native GQ when present or PL-derived REFQ, and GRCh37 X/Y/MT ploidy is sex-aware. AUTO sex/ploidy inference is audited from the target BAM and can be overridden with `DANTE_SAMPLE_SEX=M|F`. Legacy `reference-calls-v1` is intentionally stale and must be recalculated from the already-finished Stage 15 BAM.
> It also locks in the measured Home Computer Stage 15 baseline: 12 BWA threads, 4 samtools sort threads, 1536M per sort thread, 10M-read checkpoints and double-buffered FASTQ staging.
> Stage 15 uses resumable coordinate-BAM checkpoints, 10M-record double-buffered single-end chunks, MAX profile 12 BWA + 4 samtools workers with 1536M/thread sort memory on the Home Computer, disk guards, orphan-container recovery and non-spamming activity status.

> Stage 16 в v8.6.0 также корректно обрабатывает позиции GRCh37 с `N`: такие loci не получают выдуманный REF, исключаются из calling и публикуются в `Dante_reference_calls_uncallable.tsv` для аудита.
> Stage 2 item 11 scans the entire annotated variant catalog for ClinVar VUS and rare/unclassified LoF, nonsense/frameshift/splice, missense and in-frame/protein-altering variants, with CHESS 2.2 gene metadata embedded in the distribution. No hand-picked gene list is required.



Локальный Windows-конвейер для пяти GRCh37 VCF-файлов Dante Labs. Исходные
VCF и FASTQ не изменяются. Этапы 1–4 выполняются локально; этап 5 — отдельное
необязательное исследование короткого evidence-classed списка через API.

## Какой `.cmd` запускать

Для всех новых запусков используйте:

```text
start.cmd
```

Начиная с v8.6.0 в корне оставлен один launcher — `start.cmd`. Тесты разработчика запускаются через `Run-Tests.ps1`; отдельный `.cmd` для тестов больше не нужен. Старые `RUN_DANTE_*` имена удалены.

Исторически `RUN_DANTE_MINIMAL.cmd` был не другим режимом обработки. Это старое имя launcher,
оставшееся от минимальных версий v3–v6. Начиная с v7 оно запускало тот же
`dante_wgs_pipeline.ps1`, то же меню и все четыре этапа, что и
`RUN_DANTE_WGS.cmd`. До v7.4.6 оба `.cmd` были побайтно одинаковыми, поэтому
использование `RUN_DANTE_MINIMAL.cmd` не ограничивало расчёт и не привело к
потере результатов.

В v7.4.7 `RUN_DANTE_MINIMAL.cmd` оставлен для совместимости со старыми
ярлыками и привычным способом запуска. Теперь он явно сообщает, что является
compatibility alias, и передаёт управление `RUN_DANTE_WGS.cmd`.

Оба launcher выполняют только две технические функции:

1. запускают синтаксическую проверку `dante_wgs_pipeline.ps1` встроенным
   Windows PowerShell parser;
2. при отсутствии ошибок открывают одно и то же меню pipeline.

Минимальную или полную обработку выбирает не имя `.cmd`, а пункт меню:

- пункты 1–5 — минимальный этап и CNV/SV;
- пункты 6–12 — полная локальная обработка малых вариантов;
- пункты 13–18 — дополнение reference-genome слоя: сначала array-источники, затем R1 либо R1/R2;
- пункт 19 — отдельный API-этап;
- пункт 20 — локальные этапы 1+2 без API (долгий FASTQ-этап не запускается автоматически).

## Стадия 3 в v7.5.7: сначала известные array-генотипы, затем R1/R1+R2

Обычный Dante VCF и созданный пунктом 2 файл являются **variant-only**: строка
показывает найденный вариант, но отсутствие строки не доказывает генотип
`0/0`. Поэтому из такого файла нельзя честно восстановить зелёные
гомозиготно-референсные записи Promethease.

Стадия 3 повторно использует исходные чтения:

1. находит рядом со скриптом один `R1` либо ровно одну пару `R1/R2` с
   расширением `.fastq`, `.fq`, `.fastq.gz` или `.fq.gz`;
2. проверяет структуру первых записей; для paired-end также сверяет правила
   имени пары и имена mates;
3. перед первым расчётом полностью читает каждый используемый поток,
   проверяет gzip, за тот же проход вычисляет SHA256 распакованного содержимого
   и точное число FASTQ records; эти counts затем используются как знаменатель
   для реального progress пункта 15;
4. строит BWA-индекс для фактически установленного GRCh37 FASTA;
5. выполняет single-end или paired-end BWA MEM, name sort, `fixmate`, coordinate sort и
   `markdup`, после чего оставляет в BAM только чтения целевых областей;
6. вызывает генотипы bcftools с минимальными mapping quality 30 и base quality
   20;
7. публикует генотип только при `DP >= 10`, `GQ >= 30`, глубине каждого
   вызванного аллеля `AD >= 3`, доле гомозиготного аллеля не ниже 0,90 или
   доле каждого гетерозиготного аллеля 0,20–0,80. В остальных случаях пишет
   `--`.

Основной новый результат:

```text
Dante_results\Dante_23andMe_reference_complete.txt.gz
```

Старый `Dante_23andMe_style.txt.gz` не перезаписывается. Итоговый приоритет источников:

1. `Dante_23andMe_style.txt.gz` (variant-only вызов из Dante VCF);
2. строгий вызов из текущего `R1` либо `R1+R2`;
3. согласованный старый генотип из `reference_panel_sources`;
4. `--`, если надёжного генотипа нет.

Любое расхождение между этими слоями сохраняется в
`Dante_qc\Dante_reference_export_discrepancies.tsv`; выбранный источник каждой
финальной строки сохраняется в
`Dante_qc\Dante_reference_genotype_provenance.tsv`.

При одном R1 меню показывает `[READY: SINGLE-END R1]`; FASTQ-пункты 15–18 не
блокируются. Пункт 14 вообще не зависит от FASTQ. Заявленное среднее покрытие 15× не означает `DP=15` в каждой
целевой позиции: локальная глубина проверяется отдельно. Позиции, не прошедшие
строгие пороги, публикуются как `--`. Если позже рядом появляется подходящий
R2, режим входа меняется на `paired`, single-end BAM получает статус
`[STALE: FASTQ MODE CHANGED]` и пункт 15 строит его заново по двум reads.

В v7.5.7 пункт 15 выводит отдельный overall progress. Шкала этапов: FASTQ
validation `0–5%`, подготовка Docker/BWA reference `5–8%`, BWA alignment по
точному числу прочитанных sequences `8–90%`, drain/sort/markdup/target filter
`90–95%`, quickcheck/count/index/atomic publish `95–100%`. Во время BWA
показываются processed/total reads, скорость и ETA. Старый validation-state
без `record_count` один раз обновляется полным проходом FASTQ; после этого
повторные запуски используют сохранённые counts.

Закреплённые Docker images BWA/samtools/bcftools больше не выполняют
обязательный `docker pull` при каждом запуске. Если точный image уже есть
локально, он используется без обращения к registry. Если image отсутствует,
pipeline делает resumable/retry-подобные сетевые попытки и при неуспехе
останавливается, не теряя готовую FASTQ validation. Это устраняет ложное
падение на кратковременном VPN/proxy/quay.io сбое, когда image уже скачан.

Целевые позиции автоматически берутся из установленного ClinVar GRCh37.
Чтобы получить покрытие обычных chip/Promethease rsID, можно положить исходные
GRCh37 файлы 23andMe/Atlas/Genotek или отдельный manifest в папку
`reference_panel_sources`. Поддерживаются первые четыре поля:
`rsid/chromosome/position/genotype`. Четвёртое поле необязательно. Если оно
содержит A/C/G/T-генотип, он сохраняется как старое независимое измерение и
может заполнить позицию только тогда, когда Dante VCF её не содержит, а строгий
FASTQ-вызов дал `--`.

Если несколько файлов `reference_panel_sources` дают разные генотипы для одного
rsID на одной координате, ни один из них автоматически не выбирается: позиция
помечается `CONFLICT`, fallback отключается, а все варианты записываются в
`Dante_qc\Dante_reference_source_genotype_conflicts.tsv`. Если один rsID имеет
разные GRCh37-координаты, он полностью исключается из target panel, а **все**
координаты и их источники сохраняются в
`Dante_qc\Dante_reference_target_coordinate_conflicts.tsv`.

При пересборке пункта 13 неизменившийся `Dante_reference_targets.bed` не
перепубликуется. Поэтому добавление/уточнение только старых генотипов при тех же
координатах не делает уже рассчитанный R1 BAM устаревшим: достаточно пересобрать
пункт 13, затем пункт 14 для немедленного pre-FASTQ merge либо пункт 17, если строгие FASTQ calls уже существуют. Смешивать GRCh37 и GRCh38 нельзя.

## Исправление v7.4.12: внутреннее имя файлов в gzip

Атомарная запись по-прежнему выполняется через временный внешний файл
`*.part`, который становится финальным только после успешного закрытия gzip.
Ранее `gzip.open()` также помещал временное имя в заголовок самого архива.
Поэтому готовый и проверенный `Dante_23andMe_style.txt.gz` при открытии в
7-Zip показывал внутри единственный файл
`Dante_23andMe_style.txt.gz.part`, хотя данные уже были завершены.

В v7.4.12 gzip создаётся без встроенного временного имени. 7-Zip и другие
архиваторы выводят имя из финального имени архива, поэтому распаковка создаёт
`Dante_23andMe_style.txt`. Исправление не ослабляет атомарную публикацию и
распространено на другие создаваемые Python файлы `*.gz`.

Уже готовый архив v7.4.11 не повреждён: его можно распаковать и вручную убрать
суффикс `.gz.part` у извлечённого текстового файла. Пересчёт генотипов для
исправления одного имени не требуется.

## Исправление v7.4.11: viral/decoy-континги Dante VCF

В Dante SNP VCF присутствуют записи на
[`NC_007605`](https://www.ncbi.nlm.nih.gov/nuccore/NC_007605.1) — референсе
полного генома Human gammaherpesvirus 4 (Epstein–Barr virus). Это не
последовательность человеческой primary assembly GRCh37, поэтому
установленный FASTA обоснованно не содержит её, а строгий
`bcftools norm --check-ref e` останавливался при
первой такой записи.

В v7.4.11 пункт 8:

- извлекает допустимые континги непосредственно из фактически установленного
  GRCh37 FASTA;
- перед проверкой REF применяет этот список через `bcftools norm
  --targets-file`, поэтому отсутствующие viral/decoy-записи не попадают в
  человеческий каталог;
- сохраняет список целей в
  `Dante_qc\GRCh37_reference_contigs.targets.tsv`;
- сравнивает континги заголовков SNP, INDEL и RAW VCF с FASTA и пишет полный
  аудит в `Dante_qc\Dante_reference_contig_audit.txt`;
- включает SHA256 списка целей и версию политики фильтрации в state каждого

## Улучшение v7.4.5: нативный прогресс AnnotSV для CNV и SV

AnnotSV создаёт итоговый `*.part.tsv` и его заголовок в начале запуска, а затем
долго обрабатывает внутренний `*.part.tsv.tmp`. Поэтому неизменный размер
итогового файла не означал зависание и не давал полезного процента.

В v7.4.5 пункт 4 и включающие его автоматические режимы показывают:

- приблизительный общий процент по устойчивым фазам AnnotSV 3.5.10;
- текущую фазу (`load configuration`, `find gene/regulatory overlaps`,
  `main annotation pass`, `write final table`);
- реальную долю прочитанного внутреннего annotation stream во время самой
  длинной фазы; этот диапазон отображается как `~35–90%`;
- ETA после накопления двух измерений скорости чтения;
- `92%` при переходе к финальной записи и `100%` только после успешного выхода
  AnnotSV.

Процент помечен знаком `~`, потому что разные строки требуют разного числа
аннотационных пересечений. Трекер ничего не меняет внутри базы или результата:
он только читает позицию открытого файла через `/proc` контейнера. Если Docker
не отдаёт эту телеметрию, запуск продолжается штатно и остаётся поэтапный
heartbeat без выдуманного ETA.

## Требуемые Dante VCF

Минимальный этап использует три файла:

- `*.filtered.snp.vcf` или `.vcf.gz`;
- `*.cnv.vcf` или `.vcf.gz`;
- `*.sv.vcf` или `.vcf.gz`.

Полная аннотация дополнительно требует:

- `*.raw.vcf` или `.vcf.gz`;
- `*.filtered.indel.vcf` или `.vcf.gz`.

В папке должен быть ровно один файл каждой роли. Если найдено два подходящих файла, соответствующий пункт остановится, чтобы не выбрать геном молча.

Для этапов 3 и 4 нужен как минимум R1. Одиночный R1 обрабатывается как явный
single-end вход; при наличии согласованного R2 используется paired-end режим.
R1/R2 кладутся в ту же папку, что `.cmd` и VCF; перемещать их в `Dante_work`
не нужно. Single-end результат допустим как промежуточный исследовательский
расчёт, но paired-end обычно даёт более надёжное выравнивание.

## Меню

### Этап 1 — минимальный экспорт и структурные варианты

1. **Install/resume VEP 116 GRCh37 cache** — устанавливает или продолжает скачивать тот же VEP cache, который использовала v6.
2. **Create Dante_23andMe_style.txt.gz** — быстрый allele-specific поиск rsID и строгий четырёхколоночный экспорт SNP. Если VEP-архив уже скачан, но ещё не распакован, пункт автоматически завершит его проверку и установку.
3. **Install AnnotSV public annotations** — устанавливает/восстанавливает публичные базы AnnotSV и публикует `READY` только после GRCh37 smoke-test.
4. **Annotate CNV and SV with AnnotSV** — при необходимости сначала автоматически чинит базы, затем фильтрует PASS/canonical CNV и SV и создаёт подробные таблицы AnnotSV.
5. **Run complete stage 1** — выполняет пункты 1–4.

### Этап 2 — полная детерминированная аннотация малых вариантов

6. **Install GRCh37 reference FASTA** — скачивает официальный primary-assembly FASTA, проверяет gzip и распаковывает его. FASTA нужна для проверки REF, нормализации и HGVS.
7. **Install/update current ClinVar GRCh37** — скачивает текущий ClinVar VCF и индекс, сверяет официальный MD5. Повторный запуск обновит базу только при изменении MD5.
8. **Prepare normalized SNP, INDEL and residual layers** — строит список последовательностей установленного человеческого FASTA, отдельно фиксирует отсутствующие viral/decoy-континги, запускает `bcftools norm` только на совместимых GRCh37-записях, разделяет мультиаллельные строки, проверяет REF и извлекает residual после нормализации.
9. **Run full VEP annotation** — последовательно аннотирует SNP, INDEL и residual с `--everything`, HGVS, MANE/canonical transcripts, SIFT/PolyPhen, частотами и cache-клиническими полями.
10. **Build unified annotated small-variant catalog** — оставляет по одной строке на реально несомый ALT, присоединяет актуальный ClinVar точным GRCh37-ключом и пишет manifest с SHA256 входов.
11. **Build deterministic clinical/research shortlist** — разделяет клинические assertions, конфликты, фармакогеномику, ассоциации и вычислительные прогнозы по разным evidence classes.
12. **Run complete stage 2** — выполняет пункты 6–11 локально. Если VEP cache из пункта 1 отсутствует, также установит его.

### Этап 3 — reference-genome completion: array sources + R1/R2

13. **Build GRCh37 reference-genotype target panel** — объединяет SNP/rsID из текущего ClinVar и необязательных GRCh37 manifests в `reference_panel_sources`; конфликты координат исключаются.
14. **Merge known array genotypes (23andMe/Genotek/Atlas; no FASTQ)** — сразу, без R1/R2, объединяет Dante variant-only export с согласованными генотипами из `reference_panel_sources`. Приоритет на этом шаге: Dante VCF > согласованный старый генотип > `--`. Конфликты сохраняются в QC, а основной результат уже публикуется как `Dante_23andMe_reference_complete.txt.gz`.
15. **Align R1 (single-end) or R1/R2 (paired-end)** — валидирует используемые FASTQ, строит согласованный BWA index и создаёт duplicate-marked target-only BAM.
16. **Call strict reference and alternate genotypes** — вызывает и референсные, и альтернативные позиции; отсутствие достаточных данных ещё не считается `0/0`.
17. **Build tiered reference-complete export from FASTQ evidence** — обновляет тот же суммарный файл. Финальный приоритет: Dante VCF > FASTQ Tier A/B > согласованный старый генотип > `--`; Tier C сохраняется отдельно как исследовательская гипотеза.
18. **Run complete stage 3** — выполняет пункты 13–17. Получает `[READY]` только при готовности каждого подпункта.

### Этап 4 — расчёт средней длины теломер из WGS FASTQ

19. **Estimate mean telomere length and publish TXT report** — локально читает исходный R1; если найден согласованный R2, учитывает оба FASTQ. Основной результат — `Dante_results\Dante_telomere_report.txt`. Расчёт использует прозрачный TelSeq-compatible алгоритм: canonical `TTAGGG/CCCTAA`, основной порог `k>=7`, нормализация на reads с 48–52% GC и опубликованные человеческие константы TelSeq. Отдельный JSON с сырыми метриками хранится в `Dante_qc` и позволяет позже изменить дату/тип биоматериала в отчёте без повторного чтения FASTQ. Raw FASTQ не содержит BAM duplicate flags, поэтому отчёт явно маркирует результат как историческую WGS-оценку, а не лабораторное измерение.

Дата образца задаётся опционально через `.env`: `DANTE_SAMPLE_DATE=YYYY-MM-DD` или, если известен только год, `DANTE_SAMPLE_YEAR=YYYY`; тип материала — `DANTE_SAMPLE_MATERIAL=blood/saliva/...`. Если эти поля пусты, отчёт пишет `UNKNOWN` и отдельно выводит найденные date-like поля VCF как provenance clues, не выдавая их за дату забора.

### Этап 5 — ИИ-исследование доказательств

20. **Research selected shortlist variants `[API KEY REQUIRED]`** — отправляет в OpenAI API только первые строки детерминированного shortlist, а не полный геном. Перед запросами показывает число строк и требует ввести `YES`.

### Автоматизация

21. **Install and run stages 1 + 2** — выполняет VCF-часть локально. Этап 3 не включён намеренно: полное выравнивание FASTQ долгое и запускается пользователем отдельно. API не вызывается.

## Настройка `.env`

При новой установке скопируйте `.env.example` в `.env`, затем откройте `.env`
обычным текстовым редактором и замените только placeholder ключа:

```dotenv
OPENAI_API_KEY=XXXXXXXXXXX
OPENAI_MODEL=gpt-5.6
OPENAI_REASONING=high
OPENAI_MAX_VARIANTS=20

# Необязательно, для исторического telomere report:
DANTE_SAMPLE_DATE=
DANTE_SAMPLE_YEAR=
DANTE_SAMPLE_MATERIAL=
```

- API-ключ нужен только пункту 20.
- Значение ключа никогда не печатается в меню или отчётах.
- После вставки реального ключа не пересылайте `.env` и архив с ним другим людям.
- `OPENAI_MAX_VARIANTS` принимает значения от 1 до 200; по умолчанию отправляется максимум 20 shortlist-строк.
- `OPENAI_MODEL` можно менять без правки Python-кода. На момент сборки официальный alias `gpt-5.6` соответствует GPT-5.6 Sol.
- Для запросов выставлено `store=False`; дополнительно полный геном никогда не передаётся API.
- При первом API-запуске официальный Python SDK `openai` будет установлен или обновлён автоматически, если его ещё нет.

Официальная документация: [API key и Python SDK](https://developers.openai.com/api/docs/quickstart), [Responses API с web search](https://developers.openai.com/api/docs/guides/tools-web-search), [GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol).

## Возобновление после прерывания

- VEP cache, FASTA и ClinVar докачиваются с уже сохранённого байта.
- После обрыва сети загрузчики с поддержкой resume запускают новый `curl` и не откатывают прирост предыдущей попытки.
- Неполная установка AnnotSV остаётся `INCOMPLETE`; пункт 3 или 4 повторяет установку/repair и создаёт completion-marker только после успешного smoke-test.
- Распаковка VEP cache и FASTA не продолжается с середины: исходный скачанный архив сохраняется, незавершённая распаковка на повторе очищается и запускается заново.
- В пункте 2 незавершённый минимальный VEP не продолжается с середины gzip и пересчитывается. Завершённый VEP имеет отдельный state и переиспользуется, если оборвалась только конвертация.
- Финальный `Dante_23andMe_style.txt.gz` публикуется атомарно. Незавершённый `.part` никогда не получает финальное имя и не показывается как `READY`.
- Нормализованные слои переиспользуются при совпадении SHA256 исходного VCF, FASTA и списка разрешённых reference-контингов.
- Полный VEP публикует только целый gzip. Готовые слои переиспользуются; прерванный текущий слой при следующем запуске считается заново.
- Единый каталог и shortlist переиспользуются только при совпадении SHA256 входов.
- Каждый используемый FASTQ полностью проверяется и хешируется один раз;
  неизменившийся R1 или пара R1/R2 повторно не перечитываются перед продолжением этапа 3.
- BWA index, target BAM, call VCF и новый экспорт имеют раздельные state и
  публикуются только после проверок. Прерванные вычисляемые `.part` не
  продолжаются с середины, а точно пересчитываются.
- Отдельные готовые ИИ-отчёты при повторном запуске пропускаются.

## Важные ограничения

- Это исследовательский конвейер, а не медицинский диагноз.
- `HIGH impact`, SIFT или PolyPhen сами по себе не означают патогенность.
- ClinVar review stars отражают качество рецензирования записи, но не заменяют фенотип, наследование и экспертную интерпретацию.
- Exact ClinVar join может не сопоставить эквивалентный, но иначе представленный сложный вариант; такие случаи остаются без `clinvar_exact_match=yes`.
- Variant-only VCF не позволяет считать отсутствие строки доказанным `0/0` без gVCF/coverage/read-level данных.
- `--` в reference-complete файле означает no-call: недостаточное покрытие,
  качество, allelic balance, неоднозначность или отсутствие вызываемой записи.
  Это не генотип `0/0`.
- Этап 3 генотипирует целевую rsID-панель, а не создаёт «строку на каждую из
  трёх миллиардов позиций» референсного генома.
- FASTQ/CRAM не заменяются этим каталогом, если в будущем потребуется повторный variant calling другим алгоритмом.

Документация баз и инструментов: [VEP cache и offline-режим](https://grch37.ensembl.org/info/docs/tools/vep/script/vep_cache.html), [VEP FASTA/HGVS](https://grch37.ensembl.org/info/docs/tools/vep/script/vep_download.html), [ClinVar GRCh37 downloads](https://ftp.ncbi.nlm.nih.gov/pub/clinvar/vcf_GRCh37/), [bcftools](https://samtools.github.io/bcftools/bcftools.html).

Для новой стадии 3: [BWA](https://github.com/lh3/bwa),
[samtools](https://www.htslib.org/doc/samtools.html),
[samtools markdup](https://www.htslib.org/doc/samtools-markdup.html) и
[описание gVCF/reference-confidence GATK](https://gatk.broadinstitute.org/hc/en-us/articles/360035531812-GVCF-Genomic-Variant-Call-Format).

## Самопроверка релиза

`start.cmd` всегда выполняет parser-preflight до запуска меню. Для
полного набора локальных регрессионных тестов запустите `Run-Tests.ps1`: он
повторяет Windows PowerShell parser-check и затем проверяет FASTQ discovery,
битые/неполные пары, target-panel, строгие границы DP/GQ/AD/allelic balance,
явные `--`, конфликты объединения и gzip-заголовок.

## Если автоматическая проверка показывает красный статус

- `Docker CLI [NOT OK]` — Docker Desktop не установлен или `docker.exe` недоступен в `PATH`.
- `Docker engine [NOT OK]` — Docker Desktop установлен, но ещё не запущен.
- `RAW/INDEL [NOT OK]` — этап 1 можно использовать, этап 2 нельзя.
- `FASTQ input [OK] ... Single-end R1` — этап 3 может работать по одному R1.
- `FASTQ input [NOT OK]` — R1 отсутствует, неоднозначен либо FASTQ повреждён; этапы 1–2 остаются доступны.
- `OpenAI API key [NOT OK]` — этапы 1–3 полностью доступны; недоступен только пункт 19.
- Несколько VCF одной роли — удалите из рабочей папки лишнюю копию или перенесите её в другую папку.

## v7.5.11: resumable Stage 15

Stage 15 now aligns the complete FASTQ in 5,000,000-record checkpoints.  A completed
checkpoint is reused after interruption, so only the currently unfinished chunk must be
realigned.  Single-end R1 skips query-name collation entirely; paired-end R1+R2 uses
`samtools collate -> fixmate -> coordinate sort` per chunk.  All full-genome coordinate
checkpoints are then merged and passed through one global `samtools markdup`; only after
that is the final BAM restricted to the reference target BED.

The default checkpoint directory is `Dante_work\\reference_alignment_checkpoints`.
Set `DANTE_REFERENCE_CHECKPOINT_DIR` in `.env` to move it to a large/fast SSD.
A disk-space guard predicts checkpoint growth and performs a safe stop before the volume
is exhausted.  Re-running item 15 continues from the last completed checkpoint.


## v8.0: genome-wide uncertain-coding sweep + consolidated resumable Stage 15

Пункт 11 больше не использует ручной список генов. Он просматривает весь единый каталог
вариантов и отдельно публикует `Dante_results\Dante_genomewide_uncertain_coding.tsv`.
Явные ClinVar VUS функциональных coding/splice классов сохраняются без фильтра SIFT/PolyPhen;
варианты без определённой клинической классификации сохраняются для тех же молекулярных
классов при неизвестной частоте либо max AF <= 1%. Встроенный `reference_data\CHESS_2.2_genes.tsv`
используется для описания/типизации генов, но не ограничивает поиск и не смешивает координаты
CHESS с GRCh37: координатная аннотация вариантов остаётся VEP GRCh37.

Stage 15 консолидирует последние hotfix: 20M-record checkpoints, single-end FASTQ.gz streaming
прямо в BWA stdin, MAX-профиль 12 BWA workers + 4 samtools sort workers на 12-thread Home Computer,
сохранение старых 5M checkpoints при миграции, disk guard, явный RESUME SCAN и маркированные
Docker runtime containers. После Ctrl+C/сбоя новый запуск удаляет только orphan-контейнеры
Stage 15, не затрагивая другие Docker workloads. Повторяющийся `waiting for output` heartbeat
больше не печатается, пока состояние watched output реально не изменилось.

## Stage 17 confidence tiers

Stage 17 сохраняет FASTQ evidence тремя уровнями. Tier A (HIGH): DP>=10, GQ/REFQ>=30, hom AF>=0.90, het >=3 reads/allele и AF 0.20-0.80. Tier B (SUPPORTIVE): DP>=5, GQ/REFQ>=10, hom >=4 supporting reads и AF>=0.80, het >=2 reads/allele и AF 0.20-0.80. Tier C (HYPOTHESIS): DP>=5 и GQ/REFQ>=5; сохраняется для исследовательской проверки, но не публикуется как подтвержденный genotype. По умолчанию reference-complete export включает Tier A+B.


## Stage 6 — Open reference knowledge

Пункт 22 устанавливает воспроизводимый локальный bundle открытых справочников: HGNC, GenCC, ClinGen, GIAB GRCh37 stratifications, AlphaMissense hg19, Mondo, HPO ontology-only и dbSNP dual-build remote indexes/assembly reports. Полные dbSNP VCF (~54 GiB суммарно) намеренно не копируются локально.

Лицензии/атрибуции записываются в `reference_data/open_reference/open_reference_manifest.json` и `ATTRIBUTIONS.md`; эти данные предназначены для автоматической вставки в будущий PDF-отчёт. HPO disease/gene annotations с внешним provenance в этот bundle не входят.


## Stage 6 — юридическое разделение knowledge bundle

- `22` устанавливает open/commercial-safe knowledge bundle.
- `23` устанавливает `reference_data/research_reference` с `bundle_scope=RESEARCH_ONLY`, `commercial_allowed=false`, species scope `Homo sapiens`.
- Research bundle v8.6.0: PanelApp snapshot, CADD v1.7 GRCh37 tabix/remote metadata, UCSC hg19↔hg38 liftOver chains.
- PanelApp без отдельного соглашения с Genomics England нельзя использовать коммерчески, для диагностики, медицинских решений или healthcare service.
- OMIM не загружается автоматически: требуется индивидуальный API key и принятие отдельных условий.
- Будущий PDF finalizer должен формировать `knowledge_usage_manifest.json` по реально использованным источникам и вызывать `report_publication_guard.py`. COMMERCIAL report блокирует research-only sources; RESEARCH report допускает их с обязательными notices/attributions.


## Важное разделение: installation != enrichment

Stage 5 (`22`/`23`) только скачивает и фиксирует reproducible snapshots справочников.
Он не должен менять уже рассчитанные VCF/BAM/shortlist автоматически.

Следующий knowledge-enrichment stage должен работать **после** получения канонических genomic outputs
и до AI/PDF publication. Он обязан сканировать не только shortlist, а полный набор релевантных результатов:
`Dante_small_variants_annotated.tsv.gz`, CNV/SV outputs и tiered FASTQ evidence.
Поэтому поздняя установка справочников не теряет варианты: upstream data сохраняются и могут быть повторно
аннотированы. Mondo/HPO становятся активными только при наличии phenotype/context input.

v8.6.0 также отвязывает Stage 16 analytical-contract check от номера программного релиза:
housekeeping/knowledge updates больше не должны инвалидировать неизменившийся caller.


## v8.6.0 — Stage 17 Windows publication fix

Исправлен WinError 32 на 97% Stage 17 при публикации
`Dante_reference_FASTQ_evidence.tsv.gz.part`.

Причина была внутренней: `gzip.GzipFile(fileobj=...)` не закрывает переданный ему
raw file object. Старый `elif`-cleanup закрывал TextIOWrapper/GzipFile, но оставлял
raw handle открытым в самом процессе Python. На Windows это блокировало `os.replace`.

v8.6.0:
- явно закрывает TextIOWrapper, GzipFile и raw file handle;
- публикует все Stage 17 artifacts через atomic replace с коротким retry для
  временных WinError 5/32 от Defender/indexer;
- не меняет A/B/C thresholds, Stage 16 calls или Stage 17 analytical schema.

После сбоя v8.3.2 геномные входы и Stage 16 остаются валидны. Stage 17 можно просто
запустить повторно; это только streaming merge (~2 минуты на текущем наборе), без
повторного alignment/calling.

## v8.6.0 — Stage 19 optional metadata fix

Исправлен мгновенный сбой Stage 19:
`telomere_estimate.py: error: argument --sample-date: expected one argument`.

Причина: PowerShell передавал `--sample-date`, `--sample-year` и `--sample-material`
безусловно. При пустом значении функция могла не добавить второй элемент в массив
аргументов, оставляя bare option token.

Теперь:
- optional metadata flags добавляются только если значение непустое;
- Python parser дополнительно принимает bare optional metadata flag как пустое значение;
- date/year/material вычисляются один раз и теми же значениями записываются в state;
- FASTQ/calling/telomere algorithms не изменены.

Если дата образца неизвестна, Stage 19 теперь штатно считает теломеры и записывает
`UNKNOWN`; дату/год можно позже добавить через `.env` и повторно сгенерировать отчёт
из cached telomere metrics без повторного FASTQ scan.

## v8.6.0 — Windows patient-selector root quoting fix

Исправлен `WinError 123` на самом первом запуске patient selector.

Причина: `%~dp0` в Windows batch всегда оканчивается обратным слешем. Передача
`"C:\...\Full Genome Parser\"` как native/Python argument может интерпретировать
последний `\` как экранирование закрывающей кавычки, из-за чего Python получал
путь вида `C:\...\Full Genome Parser"`.

`start.cmd` теперь сначала удаляет завершающий `\` из `DANTE_ROOT` и только затем
передаёт `--root "%DANTE_ROOT%"`.

Миграция пациента ещё не началась в упавшем v8.5.0 запуске, поэтому никаких данных
исправлять или откатывать не требуется.


## v8.6.0 — PanelApp HTTP 429 recovery

Исправлен сбой пункта 23 при `HTTP Error 429: Too Many Requests`.

- PanelApp requests ограничены примерно одним запросом в секунду.
- HTTP `Retry-After` соблюдается, если он прислан сервером.

- Повторный запуск переиспользует уже сохранённые версии panels и продолжает partial snapshot,
  а не начинает все 433 панели с нуля.
- CADD, patient layout и геномные аналитические контракты не изменены.
